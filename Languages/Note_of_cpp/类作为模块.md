# 类作为模块

模块是指：从物理上对程序中定义的实体进行分组，是可以**单独编写和编译**的程序单位。

模块化是组织和管理大型程序的一个重要手段。一个模块包含接口和实现两部分：

-接口：是指在模块中定义的、可以被其它模块使用的一些程序实体的描述。

-实现：是指在模块中定义的所有程序实体的具体实现描述。

核心思想：接口与实现的分离。使用者只需要知道它“能做什么”，而不需要知道它“怎么做的”。

---

在标准的工程实践中，一个“类模块”通常由两部分组成：

头文件 (`.h`/`.hpp`)：声明接口。这是模块的“说明书”。

源文件 (`.cpp`)：实现细节。这是模块的“内部逻辑”。

示例：一个日志模块

**Logger.h (接口)**

```cpp
#ifndef LOGGER_H
#define LOGGER_H

#include <string>

class Logger {
public:
    static void log(const std::string& message); // 静态接口，方便直接调用
private:
    static void formatMessage(std::string& msg); // 内部逻辑，对外隐藏
};

#endif
```

**Logger.cpp (实现)**

```cpp
#include "Logger.h" // 包含头文件
#include <iostream>
#include <ctime>

void Logger::log(const std::string& message) {
    std::string temp = message;
    formatMessage(temp);
    std::cout << temp << std::endl;
}

void Logger::formatMessage(std::string& msg) {
    // 复杂的内部处理逻辑，比如添加时间戳
    msg = "[LOG]: " + msg;
}
```

良好的面向对象程序设计风格是什么呢？

-模块间的耦合度反映在对象类之间的关联性上。

-要降低模块间的耦合度，可以对类中成员函数能访问的对象的集合作一定的限制，并尽量使该集合为最小。

上述要求被称为**Demeter法则**。

如果把代码比作一个社交圈，Demeter法则的核心思想就是：“只和你的直接朋友说话，不要跟‘朋友的朋友’说话。” 在 C++ 类设计中，这意味着一个对象应对其他对象保持最少的了解。

---

**Demeter法则的正式定义**

对于一个对象 $A$ 中的方法 $M$，它只能调用以下类型的对象：

-对象 $A$ 本身（`this`）

-方法 $M$ 的参数对象

-在方法 $M$ 中创建的对象

-对象 $A$ 的直接成员变量

假设我们正在写一个“纸钱包”系统，如果违反迪米特法则，代码可能长这样：

```cpp
// 糟糕的设计：违反 LoD
void Transaction(Customer& customer, float amount) {
    // 逻辑：营业员直接拿走顾客钱包，翻开钱包，取钱
    // 这种“链式调用”就是典型的违反 LoD：customer -> wallet -> amount
    if (customer.getWallet().getCash() >= amount) {
        customer.getWallet().setCash(customer.getWallet().getCash() - amount);
    }
}
```

这段代码的问题在于：

-过度耦合：`Transaction` 函数不仅依赖 `Customer` 类，还必须知道 `Wallet` 类及其 `getCash` 方法。

-脆弱性：如果哪天 `Wallet` 类改名为 `Purse`，或者 `getCash` 变成了 `getBalance`，这段代码就会崩溃。

-不安全：顾客不希望营业员直接操作自己的钱包。

我们需要将逻辑回归到它所属的对象中。营业员应该只向顾客要钱，至于钱是从钱包里拿还是从袜子里翻，营业员不需要关心。

```cpp
// 遵循 LoD 的设计
class Customer {
public:
    void pay(float amount) {
        if (my_wallet.hasEnough(amount)) {
            my_wallet.deduct(amount);
        }
    }
private:
    Wallet my_wallet; // 直接朋友
};

void Transaction(Customer& customer, float amount) {
    // 营业员只跟直接朋友 (customer) 说话
    customer.pay(amount); 
}
```

LoD的缺点：

-“中间人”方法过多：为了转发请求，类中可能会多出许多琐碎的包装函数（Wrapper Methods），导致类体变得臃肿。

-性能微损：多了一层函数调用。
